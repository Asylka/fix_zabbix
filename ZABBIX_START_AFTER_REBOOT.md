# Согласованный сценарий: disable → перезагрузка VM → один запуск и 5 минут диагностики

Актуальный план от 21.10.2026. Перезагрузку VM выполняет владелец. Маску, очистку процессов через kill и изменение фаервола в этом сценарии не используем. Второй сервер остаётся выключенным. Работа ведётся с существующей установкой и базой, без переустановки или очистки данных.

## 1. До перезагрузки VM

На Linux VM Zabbix:

```sh
sudo systemctl unmask zabbix-server.service
sudo systemctl disable zabbix-server.service
systemctl is-enabled zabbix-server.service
```

`unmask` нужен, если маска была установлена ранее; сам службу не запускает. Ожидаемый результат проверки — `disabled`. Ненулевой код `is-enabled` в этом случае нормален. `disable` отключает обычный автозапуск, но не останавливает текущую службу и не запрещает ручной запуск или запуск внешней автоматизацией. См. [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html).

Сохранить имеющуюся диагностику вне VM. Затем самостоятельно перезагрузить **VM/гостевую ОС**, а не выполнять `systemctl restart zabbix-server`. В сохранённом снимке `TimeoutStopUSec=infinity`, поэтому штатное выключение может зависнуть на остановке службы. Скрипт ниже это зависание не устраняет и перезагрузкой не управляет.

## 2. После загрузки VM

Не выполнять отдельный `systemctl start`: его один раз выполнит скрипт.

Перенести **один файл** `zabbix_start_observe.sh` в `/root/zabbix_start_observe.sh` через WinSCP/SCP или доступный канал передачи файлов. Интернет, установка пакетов и файлы `tests` не нужны. Предыдущий `zabbix_recover_v3.sh` для этого запуска не требуется.

Если переход из HA в standalone ещё не выполнен, сделать его до запуска: проверить фактический конфиг в `systemctl cat zabbix-server.service`, сохранить копию и убрать непустой `HANodeName`, включая подключаемые `Include`-файлы. Ранее согласованный `NodeAddress` оставить. Скрипт HA-настройки не редактирует; в исходной локальной копии `HANodeName` ещё был задан. Порядок перехода описан в [документации Zabbix](https://www.zabbix.com/documentation/6.0/en/manual/concepts/server/ha).

Проверить синтаксис файла:

```sh
sudo sh -n /root/zabbix_start_observe.sh
```

При отсутствии ошибок запустить:

```sh
sudo sh /root/zabbix_start_observe.sh --start
```

Терминал держать открытым до вывода пути архива. Наблюдение длится **300 секунд от отправки команды запуска**, даже если служба не запустилась. Подготовка, заключительный сбор и упаковка занимают дополнительное время. При отказе предварительной проверки запуска не будет; вместо ожидания пяти минут сразу собирается отчёт об отказе.

Скрипт рассчитан на стандартный локальный сервис `zabbix-server.service`, TCP 10051, конфиг `/etc/zabbix/zabbix_server.conf` и лог `/var/log/zabbix/zabbix_server.log`. Если фактические пути отличаются, диагностические источники можно указать явно:

```sh
sudo sh /root/zabbix_start_observe.sh --start \
  --config /фактический/путь/zabbix_server.conf \
  --log-file /фактический/путь/zabbix_server.log
```

Эти параметры не меняют `ExecStart` или конфигурацию службы. `Include` автоматически не разворачивается. Отсутствие файл-лога при `LogType=system` допустимо, но будет отмечено как пробел в сборе; журнал systemd собирается отдельно.

## Что делает скрипт

- Проверяет `disabled`, отсутствие маски, состояние inactive/failed, нулевые MainPID/ControlPID, отсутствие заданий службы, процессов `zabbix_server` и слушателя 10051. При неизвестном состоянии отказывает в запуске.
- Создаёт отдельный runtime drop-in `/run/systemd/system/zabbix-server.service.d/zzzz-start-observe.conf` с `Restart=no` и проверяет фактическое значение. Чужой файл с таким именем не перезаписывает. Повторно проверяет состояние перед запуском.
- Один раз отправляет `systemctl start --no-block`. Возврат этой команды означает только результат постановки задания; состояние запуска проверяется в течение наблюдения. Нет повторных start, restart, stop, kill, enable, mask, SQL или изменений iptables.
- Примерно раз в 10 секунд сохраняет состояние службы и владельцев порта; примерно раз в минуту — процессы, память, давление на ресурсы, показатели cgroup и хвост лога. Медленные команды ограничены по времени, поэтому интервалы не являются точным таймером.
- После наблюдения собирает журналы systemd/ядра за интервал запуска и выборку файл-лога, включая числовые ротации `.gz`. Вывод каждого источника ограничен 16 MiB; ограничения и ошибки чтения видны в отчёте. Нестандартные имена ротаций не охватываются.
- Записывает падение службы, изменение MainPID/InvocationID и автоматические рестарты. Выделяет сообщения, похожие на OOM, падения дочерних процессов, ошибки БД, нехватку места/FD и ошибки конфигурации. Текстовые совпадения — кандидаты для анализа, а не безошибочная классификация. Ошибки отдельных агентов не приравниваются автоматически к падению сервера.
- Проверяет итоговое состояние, живой MainPID и принадлежность слушателя cgroup службы; сохраняет запрос HA-статуса, если доступен бинарник и MainPID. HA standby без слушателя требует отдельной интерпретации.

`Restart=no` остаётся после завершения, включая неудачный старт, чтобы автоматика не скрыла первый сбой. Это временное изменение политики перезапуска, а не запрет ручного запуска. Внешний watchdog/администратор всё ещё может запускать службу; не выполнять параллельные команды управления Zabbix. Основание для политики — [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).

Окончание наблюдения не останавливает работающий Zabbix. Успешное состояние процесса не доказывает, что все метрики актуальны или очередь Proxy разобрана: эти проверки выполняются отдельно после анализа.

## 3. Какой файл передать

В конце появится строка:

```text
SEND THIS ARCHIVE: /var/log/zabbix-start-observe/ДАТА-ВРЕМЯ-PID.tar.gz
```

Скачать **этот `.tar.gz`** на рабочий компьютер и передать в этот чат. Программы для отправки и доступ в интернет на сервере не требуются. Архив содержит `SUMMARY.txt`, `critical-events.txt`, `log-findings.txt`, `timeline.tsv`, снимки состояния, исходный контекст журналов и коды завершения сборщиков. Права файлов ограничены root; скачивать через разрешённый административный доступ, не делать отчёт общедоступным.

Внутренние адреса, имена хостов и тексты журналов остаются в отчёте. Типичные строки с паролями/токенами фильтруются, но полной гарантии удаления всех секретов нет. Если упаковка не удалась, сохранить весь указанный каталог отчёта; неполный `.tar.gz` не считать готовым. При прерывании HUP/INT/TERM скрипт пытается упаковать частичный отчёт, но при аварии VM это не гарантируется.

Коды выхода: `0` — служба работает в конце, классифицированных критических признаков и пробелов сбора не отмечено; `1` — признаки сбоя/критические кандидаты; `2` — запуск отклонён или не удалось подготовить его; `3` — сбор неполный; `130` — сбор прерван. При любом из них читать `SUMMARY.txt`; отсутствие совпадений по шаблонам не означает отсутствия всех возможных ошибок.

Не повторять `--start` для уже работающего или зависшего экземпляра. Если понадобится ещё пять минут сбора без каких-либо изменений службы:

```sh
sudo sh /root/zabbix_start_observe.sh --diagnose-only
```

## 4. После анализа и подтверждения стабильности

Только после проверки свежих данных и стабильной работы убрать **именно созданный этим скриптом** временный файл и вернуть автозапуск:

```sh
sudo cat /run/systemd/system/zabbix-server.service.d/zzzz-start-observe.conf
sudo rm -- /run/systemd/system/zabbix-server.service.d/zzzz-start-observe.conf
sudo systemctl daemon-reload
sudo systemctl show zabbix-server.service -p Restart
sudo systemctl enable zabbix-server.service
systemctl is-enabled zabbix-server.service
```

Проверка файла нужна, чтобы не удалить чужую настройку. Если VM успела перезагрузиться, runtime-файл может уже отсутствовать. `daemon-reload` и `enable` не перезапускают работающий Zabbix. `systemctl revert` не применять: он может убрать другие настройки администратора.

## Проверка подготовленного скрипта

Выполнен синтаксический разбор shell и локальные тесты на искусственных данных: отказы предварительных проверок, запрет повторного запуска при изменении состояния, единственная отправка start, фиксация отказа без повторов, интервал наблюдения, разбор ошибок и ротаций, фильтрация секретов. Реальных systemd/cgroup Linux VM в локальной среде Windows нет; интеграционная проверка выполняется первым запуском на сервере. Тестовые файлы на сервер не переносить.
