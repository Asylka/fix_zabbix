# Безопасная остановка и повторный запуск Zabbix

Скрипт `zabbix_safe_restart.sh` подготовлен для вашей установки: Ubuntu 24.04,
systemd 255, Zabbix Server 6.0, `zabbix-server.service`, cgroup v2,
порт 10051. На сервер переносится **только этот один `.sh`-файл**.
Интернет, установка пакетов и перенос тестов не нужны.

Версия 1.2 исправляет обработку ошибки, показанной на фото 22.10.2026:
`Failed to list jobs: Message recipient disconnected from message bus without replying`.
При сбое чтения состояния выполняются максимум три попытки с паузами 5 секунд;
каждая команда дополнительно ограничена своим тайм-аутом. Повторяются только
проверки, а не команды start/stop/kill. После трёх неудач действия блокируются,
даже если разрешён принудительный режим. Это исправляет обработку кратковременных
сбоев связи, но не устраняет неизвестную пока причину зависания пуллеров/systemd.
Существующий runtime-файл предыдущей версии совместим и не требует удаления.

В архиве `20261022-123816-7BiFQD` подтверждены одновременно работающие
`unattended-upgrade`, `dpkg` и обновление systemd с `255.4-1ubuntu8.17` до
`255.4-1ubuntu8.18`. В 12:39:31 произошёл повторный запуск менеджера systemd,
совпавший по времени с обрывом запроса. Поэтому версия 1.2 также проверяет
процессы установки пакетов и состояние `apt-daily-upgrade.service` перед
управлением службой, запуском и дополнительными сигналами. При активном
обновлении она отказывает с диагностикой: сначала дождитесь окончания обновления.
Самостоятельно останавливать или убивать apt/dpkg скрипт не будет. Проверки
не запрещают внешней автоматизации начать обновление позже.

## Что выполнить сейчас

### Архив 15:13: обновление осталось живо после остановки службы

В `20261022-151341-0gCbmD` версия 1.2 корректно отказала **до любых действий**:
stop=0, start=0, SIGKILL=0. Статус `failed` у `apt-daily-upgrade.service`
не означает, что исчезли дочерние процессы. В снимке остались:

```text
18371 (PPID=1) apt.systemd.daily
  18401 unattended-upgrade
    115993 unattended-upgrade
      116078 unattended-upgrade
        ... needrestart (116100)
          systemctl restart ... zabbix-server.service (116132)
```

Последний `systemctl` ждёт 34 минуты; в очереди — restart Zabbix `7155`.
Главный Zabbix PID завершился ещё в 12:05:59 с кодом 1; 1227 старых процессов
остаются в прежней cgroup, MainPID=0, D-state=0. Свежего запуска не было.
Первоначальная причина выхода Zabbix пока не установлена: приложение в момент
12:05:59 в новых архивах не записано. Отключение таймера не завершает осиротевшие
процессы обновления, а отмена одного задания может позволить обновлению дойти
до следующего вызова needrestart.

Обновлённый **`zabbix_cancel_stuck_restart.sh`, версия 1.1**, поддерживает
`--drain-upgrade`. Замените только этот файл на сервере в
`/home/aliwka/zabbix_cancel_stuck_restart.sh` и выполните:

```bash
sudo bash -n /home/aliwka/zabbix_cancel_stuck_restart.sh && sudo bash /home/aliwka/zabbix_cancel_stuck_restart.sh --drain-upgrade
```

Новый режим требует уже отключённый и неактивный `apt-daily-upgrade.timer`.
Он проверяет неизменность зависшей инстанции Zabbix (InvocationID, MainPID=0,
stop-sigterm, cgroup), актуальный номер задания и цепочку процессов
`unattended-upgrade → needrestart → systemctl restart ... zabbix-server.service`.
Проверки повторяются перед каждой отменой. Допускается до 6 разных заданий
за 300 секунд ожидания; каждая команда имеет отдельный тайм-аут. Один и тот же
номер после попытки отмены повторно не отменяется. Ошибка отмены, изменение
инстанции или непроверенный источник запроса останавливают работу.

После исчезновения пакетных процессов и задания Zabbix нужен период наблюдения
30 секунд, затем пустой успешный `dpkg --audit` и ещё одна проверка состояния.
Код 0 означает готовность к отдельному восстановлению Zabbix. Он **не означает**,
что все обновления были установлены успешно, или что Zabbix уже работает.
Помощник не убивает apt/dpkg, не завершает процессы Zabbix, не запускает службы,
не меняет конфигурацию needrestart и не исправляет пакеты автоматически.

Только после `Exit code: 0` у помощника:

```bash
sudo bash -n /home/aliwka/zabbix_safe_restart.sh && sudo bash /home/aliwka/zabbix_safe_restart.sh --restart --force-after-timeout --grace-seconds 60
```

При ненулевом коде помощника основной перезапуск не выполнять; передать архив
из `SEND THIS ARCHIVE`. Теперь помощник также сохраняет журналы обновления и
Zabbix, снимки цепочки процессов, проверки таймера и результат аудита пакетов.
По каждому отменённому заданию есть отдельная папка `cancel-N`.
Архив содержит внутренние адреса и имена; фильтрация секретов ограниченная.

Локально проверяются синтаксис и подставные сценарии повторных заданий,
смены инстанции, чужого источника restart, осиротевших пакетных процессов,
лимитов, сбоев чтения/отмены и результатов dpkg audit. Это не испытание
на настоящем systemd или production-сервере.

### Если unattended-upgrade ждёт зависший restart Zabbix

В архиве `20261022-125705-gh6DTk` обнаружен отдельный сценарий:
`unattended-upgrade → needrestart → systemctl restart ... zabbix-server.service`.
В systemd осталось задание `4126 zabbix-server.service restart running`.
Версия 1.2 отказывает из-за работающего обновления, но обновление само ждёт
Zabbix. Одно ожидание завершения обновлений не разрывает эту зависимость.

Для этого случая подготовлен `zabbix_cancel_stuck_restart.sh`. Перенесите его
в `/home/aliwka/zabbix_cancel_stuck_restart.sh` и выполните:

```bash
sudo bash -n /home/aliwka/zabbix_cancel_stuck_restart.sh && sudo bash /home/aliwka/zabbix_cancel_stuck_restart.sh
```

Скрипт дважды проверяет `deactivating/stop-sigterm`, MainPID=0, cgroup,
InvocationID и **актуальный** номер задания. Он отменяет ровно одно running
restart-задание Zabbix. Номер 4126 из старого архива не зашит в код.
Он не завершает apt/dpkg, не посылает сигналы пуллерам и не запускает Zabbix.
В режиме без аргументов при изменившемся состоянии или ошибке чтения он
отказывает. Если задание возникло заново в финальном снимке, это фиксируется
без повторной отмены. Отмена задания должна
освободить ожидающий systemctl; завершение всего обновления проверяется отдельно.

После успешной отмены проверить:

```bash
sudo systemctl list-jobs --no-pager
sudo systemctl is-active apt-daily-upgrade.service
```

Не запускать восстановление параллельно с ещё работающим обновлением. Когда
обновление завершится, использовать основной скрипт с принудительным режимом,
если оставшиеся процессы по-прежнему не завершаются:

```bash
sudo bash /home/aliwka/zabbix_safe_restart.sh --restart --force-after-timeout --grace-seconds 60
```

Если `apt-daily-upgrade.service` завершился с ошибкой, сохранить его журнал
и проверить результат обновления; отмена restart не гарантирует успешный статус
всей пакетной операции. Отчёт помощника сохраняется в
`/var/log/zabbix-restart-job-cancel/`; при отказе нужен его каталог.

Ниже — обычный сценарий, когда пакетное обновление не ждёт Zabbix.

Перенесите файл в `/root/zabbix_safe_restart.sh`. В отдельной административной
сессии не выполняйте параллельные start/stop/restart. Терминал держите открытым
до строки `SEND THIS ARCHIVE`. Сначала проверьте синтаксис:

```bash
sudo bash -n /root/zabbix_safe_restart.sh
```

Затем выполните штатную остановку и один запуск:

```bash
sudo bash /root/zabbix_safe_restart.sh --restart
```

Скрипт сохраняет исходную диагностику, отправляет `stop --no-block` и ждёт
до 300 секунд. При зависании сохраняет дополнительный снимок, отправляет
SIGTERM всем оставшимся процессам **этой службы** и ждёт ещё до 60 секунд.
Если они не завершились, скрипт заканчивает работу с архивом и **не запускает
новый экземпляр**. Это нормальный защитный отказ, а не повод повторять
обычный `systemctl start` поверх оставшихся пуллеров.

Если остановка снова зависла и допустима потеря метрик, которые Zabbix ещё
не успел записать из памяти, используйте явный режим принудительного завершения:

```bash
sudo bash /root/zabbix_safe_restart.sh --restart --force-after-timeout
```

Он повторяет штатное ожидание, затем SIGTERM; только после этого разрешает
SIGKILL через systemd для `zabbix-server.service` и ждёт ещё до 60 секунд.
Он не применяет `killall`, `pkill` и не убивает процессы по списку старых PID.
Если даже после SIGKILL процессы остались, запуск запрещается. Для процессов
в состоянии `D` часто требуется восстановить зависший I/O; повторение сигналов
не гарантирует их исчезновения. Перезагрузку скрипт не выполняет.

Полный перезапуск обычно занимает время остановки плюс 5 минут наблюдения.
Сбор диагностики и упаковка занимают дополнительное время. Лимиты ожидания
относятся к циклам скрипта: обработка команды systemd не отменяется просто
из-за выхода скрипта, и служба может остаться `deactivating`/`activating`.

## Другие режимы

Только остановить службу, без последующего запуска:

```bash
sudo bash /root/zabbix_safe_restart.sh --stop
```

Только запустить, если старый экземпляр полностью отсутствует:

```bash
sudo bash /root/zabbix_safe_restart.sh --start
```

Только наблюдать и собрать диагностику, без управления службой и изменения
её runtime-политики:

```bash
sudo bash /root/zabbix_safe_restart.sh --diagnose
```

При необходимости можно увеличить время штатной остановки и наблюдения:

```bash
sudo bash /root/zabbix_safe_restart.sh --restart --grace-seconds 600 --observe-seconds 600
```

Времена принимаются в диапазоне 30–3600 секунд. Для нестандартной установки
есть `--config /путь`, `--log-file /путь` и `--port 10051`.
Это пути диагностических источников и проверяемый порт: они **не меняют
ExecStart** службы. Include-файлы автоматически не разворачиваются.

## Почему служба останавливается, а пуллеры остаются

`deactivating` означает, что остановка ещё идёт. Исчезновение главного процесса
или `MainPID=0` не доказывает исчезновение дочерних процессов.
`inactive/dead` с оставшимися процессами также требует проверки их принадлежности:
это могут быть остатки cgroup или экземпляр, запущенный вне этой службы.

Поэтому перед запуском проверяются одновременно:

- состояние `inactive` или `failed`, MainPID и ControlPID равны нулю;
- отсутствие всех обнаруженных процессов `zabbix_server` на этой VM;
- отсутствие процессов в cgroup службы и её подгруппах;
- отсутствие заданий systemd для службы;
- отсутствие слушателя проверяемого TCP-порта.

Скрипт отказывает в управлении, если обнаруживает `zabbix_server` вне
`/system.slice/zabbix-server.service`, включая неизвестную принадлежность.
Флаг принудительного завершения это правило не отменяет: сначала нужно
разобраться, кем и как запущен такой экземпляр. Данные будут в
`before-processes.tsv`, `before-process-details.txt`, `current-*` и `timeline.tsv`.

## Что изменяется и сохраняется

Для режимов start/stop/restart создаётся отдельный временный файл:

```text
/run/systemd/system/zabbix-server.service.d/zzzzzz-safe-restart.conf
```

Его содержимое:

```ini
# Owned by zabbix_safe_restart.sh v1; retained for operator review.
[Service]
Restart=no
SendSIGKILL=no
KillMode=control-group
KillSignal=SIGTERM
TimeoutStopSec=infinity
```

`Restart=no` предотвращает цикл автоматических запусков, скрывающий первый сбой.
`SendSIGKILL=no` отключает штатную эскалацию systemd до SIGKILL; явный флаг
скрипта разрешает отдельную команду SIGKILL. Собственные ожидания скрипта
ограничены независимо от `TimeoutStopSec=infinity`. Уже отправленные до
запуска скрипта сигналы или действия другой автоматизации отменить невозможно.

**Этот файл остаётся после завершения, в том числе успешного.** До его удаления
на работающей VM сохраняется изменённая политика. Файл в `/run` исчезает после
перезагрузки, но сама перезагрузка не исправляет постоянные настройки службы.

Скрипт не изменяет HA, базу данных, конфиг Zabbix, firewall, автозапуск,
маскировку службы; не удаляет PID-файлы и не останавливает PostgreSQL.
`--stop` означает остановку сейчас, а не постоянное отключение автозапуска.

Ваш предыдущий архив содержал `HANodeName=zabbixsrv2`. Скрипт предупредит об
этом параметре, но сохранит HA. Если нужен переход в standalone, это отдельное
изменение конфигурации после проверки остальных HA-узлов. HA standby может быть
живым без порта 10051; такой результат не считается успешным запуском сервера,
принимающего данные. Посмотрите `final-ha-status.txt` и новые логи.

После проверки стабильности, свежих метрик и очередей убрать **только этот**
runtime-файл можно так. Укажите реальный каталог отчёта из текущего запуска:

```bash
sudo bash -c '
report=/var/log/zabbix-safe-restart/КАТАЛОГ_ИЗ_ВЫВОДА
dropin=/run/systemd/system/zabbix-server.service.d/zzzzzz-safe-restart.conf
cmp -s "$report/expected-policy.conf" "$dropin" || { echo "File differs or report is missing; refusing removal"; exit 1; }
rm -- "$dropin" || exit 1
systemctl daemon-reload || exit 1
systemctl show zabbix-server.service -p Restart -p SendSIGKILL -p TimeoutStopUSec -p UnitFileState
'
```

Предыдущий скрипт также мог оставить
`/run/systemd/system/zabbix-server.service.d/zzzz-start-observe.conf` с `Restart=no`.
Новый скрипт чужой файл не удаляет: проверьте его отдельно по инструкции
`ZABBIX_START_AFTER_REBOOT.md`. Удаление нового файла не отменяет старый.
Автозапуск возвращайте только после проверки восстановления; скрипт его не включает.

## Что находится в архиве

В конце будет показан путь вида:

```text
SEND THIS ARCHIVE: /var/log/zabbix-safe-restart/20261022-120000-XXXXXX.tar.gz
```

В первую очередь смотреть:

| Файл | Назначение |
|---|---|
| `SUMMARY.txt` | Итог, код выхода, выполнялся ли start/stop, запрашивался ли SIGKILL |
| `run.log` | Последовательность действий и состояние каждые примерно 30 секунд |
| `critical.txt`, `warnings.txt` | Ошибки и предупреждения |
| `timeline.tsv` | Главный PID, число процессов, чужие процессы, D-state, cgroup, порт, задания |
| `before-*`, `stop-timeout-*`, `after-term-*`, `after-kill-*`, `final-*` | Снимки до и после соответствующих этапов |
| `before-unit-journal.txt` | Последние 3000 записей службы за текущую загрузку, включая события до запуска скрипта |
| `start-new-log.txt` | Новые записи файл-лога после отправки start |
| `stop-new-log.txt` | Записи этапа остановки, отдельно от старта |
| `previous-log-tail.txt` | Старый хвост лога, не выдаваемый за ошибки нового старта |
| `start-journal.txt`, `unit-journal.txt`, `kernel-journal.txt` | Журналы systemd/ядра |
| `log-findings.txt` | Кандидаты: OOM, падения процессов, БД, кеши, FD, место, ошибки проверок |
| `collection-gaps.txt`, `captures.tsv` | Пробелы сбора, ограничения, коды команд |
| `inspection-errors.log`, `inspection-failure-*` | Ошибки чтения состояния и сохранённые частичные снимки до повторной проверки |
| `systemd-manager-journal.txt`, `dbus-journal.txt` | Журналы PID 1 и службы D-Bus для разбора ошибок связи |
| `package-active.txt`, `package-unit.txt` | Найденные процессы установки пакетов и состояние автоматического обновления |

Чтение большого старого лога целиком устранено: сохраняется позиция открытого
файла перед действиями, затем читаются новые диапазоны байтов. Обрабатываются
смена inode и обнаруженное усечение. Очень быстрые повторные ротации или
copytruncate между проверками могут оставить пропуски. За один сбор читается
не более 32 MiB новых записей, за один диапазон — 2 MiB; превышения отмечаются.
Журналы ограничены последними 4000 записями службы и 2000 записями ядра.

Пароли и типичные секреты фильтруются построчно, но это не полная анонимизация.
В архиве остаются внутренние адреса, имена хостов и аргументы процессов.

| Код | Значение |
|---|---|
| 0 | Служба и её порт прошли наблюдение; для `--stop` — полная остановка подтверждена |
| 1 | Обнаружен сбой или критический кандидат в журнале |
| 2 | Действие отклонено, либо остановка не завершилась; повторный start не выполняется |
| 3 | Сбор неполный или не удалось создать архив; читать каталог отчёта |
| 130 | Сбор прерван сигналом; скрипт пытается сохранить архив |

Предупреждения об отдельных метриках не обязательно меняют код 0. Успешный
код не доказывает запись метрик в БД, отсутствие потерь, состояние удалённых
HA-узлов или разбор накопленной очереди Proxy. Это проверяется по свежим данным
и очередям отдельно. Если start завис, скрипт не посылает ему SIGKILL автоматически.

## Проверка перед передачей

Синтаксис проверяется `bash -n`. Локальные регрессионные тесты используют
подставные состояния и команды; они проверяют блокировку повторного запуска,
условный reset-failed, последовательность остановки и запрет неконтролируемых
сигналов. Это не интеграционный запуск на Linux VM: реальный systemd, PostgreSQL
и Zabbix здесь не запускались.
